# Production Deployment Guide

## Overview

`setup-production.sh` builds a complete, self-contained Docker deployment of
Turnstone inside this `deploy/auto-deployment/` folder. It either uses the
released images from `ghcr.io/turnstonelabs/turnstone` or builds the images
locally from a chosen source branch, fronts the dashboard with the bundled
Caddy service for HTTPS, prepares the host workspace directory the server
nodes mount at `/workspace`, and generates every file needed so the stack
starts with a single `docker compose up -d` from this folder.

The committed contents of this folder are only:

| File | Purpose |
|------|---------|
| `setup-production.sh` | Interactive deployment builder |
| `deployment.md` | This guide |

Everything else is generated by the script and ignored by Git:

| Generated file | Purpose |
|----------------|---------|
| `compose.yaml` | Production stack (Postgres, console, server, channel, Caddy, SearxNG) |
| `compose.override.yaml` | Deployment-specific adjustments (extra server nodes, OIDC wiring, public HTTPS, locally built image pinning). Docker Compose loads it automatically. |
| `tls.compose.yaml` | Service-to-service mTLS overlay (only when TLS is enabled). The script sanitizes the copy: the console `command:` override from the upstream overlay is removed because it carries a `--poll-interval` flag the console CLI no longer accepts (the console falls back to the base compose command). |
| `Caddyfile` | Browser TLS termination for the dashboard |
| `caddy/Dockerfile` | Caddy image with a DNS-challenge plugin (only for public DNS) |
| `traefik/` | Traefik static config, dynamic middlewares, and ACME storage (only when Traefik is deployed with the stack) |
| `config/turnstone-oidc.env` | OIDC settings (only when SSO is enabled) |
| `searxng/` | Bundled SearxNG configuration for the `web_search` tool |
| `workspace/` | Host directory the server nodes mount at `/workspace` (default location; see [Workspace directory](#workspace-directory)) |
| `.env` | Secrets and image tag |
| `setup-production.env` | Persistent answers file — see [Answers file](#answers-file) |

## Prerequisites

- A Linux host with Docker Engine and the Docker Compose v2 plugin
- To build the images from source: `git` and the repository's root
  `Dockerfile` (both present in a full clone), plus disk space for the build
- For a public deployment: a DNS record for the chosen hostname pointing at
  this host, ports 80 and 443 reachable from the internet, and API
  credentials for the DNS provider (Cloudflare, Route 53, or Duck DNS)
- For SSO: a confidential OIDC client registered at the identity provider
  with the redirect URI `https://<turnstone-host>/v1/api/auth/oidc/callback`
- The repository cloned locally:

```bash
git clone https://github.com/turnstonelabs/turnstone.git ~/turnstone
cd ~/turnstone
```

## Running the script

```bash
cd deploy/auto-deployment
./setup-production.sh
```

### Order of operations

1. **Git ignore sync** — before any prompt, the repository-root `.gitignore`
   is checked for the generated deployment paths (`compose.yaml`,
   `compose.override.yaml`, `tls.compose.yaml`, `Caddyfile`, `caddy/`,
   `config/`, `searxng/`, `workspace/`, `setup-production.env`, `.env`, and
   `override.compose.yaml`). Any path not already ignored is appended; nothing
   existing is modified.
2. **Deployment mode** — production or development. Choosing development
   ends the script and directs you to `./run.sh` in the repository root,
   which starts the local development stack.
3. **Project name** (yes/no) — give this deployment a custom Compose project
   name so a test stack can run beside production. See
   [Project name](#project-name).
4. **Image source** — build the images from source, or use the prebuilt
   images. See [Image source](#image-source).
5. **Image tag** (prebuilt only) — track the rolling `latest` image, or pin
   a released tag. The pinned path looks up the newest release tag
   automatically and lets you confirm or replace it.
6. **Server nodes** — how many `turnstone-server` nodes to run (default: 1).
   See [Server nodes](#server-nodes).
7. **Workspace directory** — the host directory every server node mounts at
   `/workspace` (default: `workspace/` inside this folder). See
   [Workspace directory](#workspace-directory).
8. **OIDC single sign-on** (yes/no) — see below.
9. **TLS** (yes/no) — enables mutual TLS between the Turnstone services via
   the `tls.compose.yaml` overlay (an init container bootstraps an internal
   CA; services auto-provision certificates through the console's ACME
   endpoint — see `docs/tls.md`).
10. **Reverse proxy** — `caddy` or `traefik`. See
    [Dashboard front end](#dashboard-front-end).
11. **LLM backend** (yes/no) — bootstrap default for an OpenAI-compatible
    backend. Backends can also be connected later in the console Models tab.
12. **Channel gateway** (yes/no) — Discord and/or Slack tokens.
13. **File generation** — the stack files are copied into this folder, the
    overlays and proxy configuration are written, and secrets
    (`TURNSTONE_JWT_SECRET`, `POSTGRES_PASSWORD`) are preserved from the
    existing `.env` if present, or generated fresh on a first run.

Answering **no** to every optional section still produces a safe and secure
deployment: random secrets, the dashboard served over HTTPS on
`https://localhost:8443` via Caddy's local CA, and no ports published beyond
Caddy and localhost-bound Postgres.

### Project name

By default the stack runs as the Compose project `turnstone`. Answering yes
lets you name it something else, which is written to `.env` as
`COMPOSE_PROJECT_NAME` and takes precedence over the `name:` attribute in
`compose.yaml`.

The project name prefixes every container, network, and volume, so a second
deployment (for example `turnstone-test`) runs beside production without
colliding.

> **Changing the name on an existing deployment starts from empty volumes.**
> `turnstone_postgres-data` and `turnstone-test_postgres-data` are different
> volumes. The script warns when the new name has no data volume yet while
> the default one does; the old data is left untouched, not migrated.

Under `AUTORUN=true` the recorded answer is reused, so an automated run keeps
whatever name the last interactive run chose.

### Dashboard front end

After the TLS question the script asks which reverse proxy terminates browser
HTTPS.

**`caddy`** (default) uses the bundled Caddy service. It then asks whether to
serve a public DNS name: answering no keeps the dashboard on
`https://localhost:8443` with Caddy's local CA, and answering yes asks for the
hostname, a Let's Encrypt registration email, and a DNS-01 challenge provider,
then writes a `Caddyfile` and a `caddy/Dockerfile` that builds Caddy with the
matching DNS plugin.

**`traefik`** then asks whether Traefik should be deployed as part of this
stack. Answering **no** means Traefik already runs on this system:

- You supply the hostname, the existing Docker network shared with Traefik
  (default `frontend`), the router/service name, the entrypoint, and an
  optional certresolver.
- `compose.override.yaml` joins `console` to that network and publishes the
  matching `traefik.*` labels. Traefik reaches the console on port 8090.
- The bundled `caddy` service is disabled with an unused profile and its
  published port is dropped with `ports: !reset null`, so it cannot clash
  with the proxy. This stack then publishes no ports at all.
- The script warns if the named network does not exist yet.

Answering **yes** deploys Traefik alongside Turnstone:

- You supply the hostname, router name, ACME email, and a DNS-01 provider
  with its credentials, plus an optional extra external network for Traefik
  to serve other stacks on.
- `traefik/traefik.yaml` and a `traefik` service are generated. Traefik owns
  ports 80 and 443, redirects HTTP to HTTPS, and resolves certificates
  through the chosen DNS provider.
- **Web UI:** offered only when OIDC is configured, because the dashboard has
  no authentication of its own. When enabled you supply its hostname and a
  forward-auth endpoint, and `traefik/dynamic/middlewares.yaml` is generated
  with a `dashboard-auth` middleware that the dashboard router requires. When
  OIDC is not configured the script warns, and `traefik.yaml` is written with
  `dashboard: false` under a comment stating that the web UI needs proxy
  protection before being enabled.

`!reset` requires Docker Compose 2.24 or newer.

### Image source

The image source question decides where the Turnstone images come from:

- **`prebuilt`** (default) — the stack runs the released
  `ghcr.io/turnstonelabs/turnstone` images, and the image tag question
  chooses between the rolling `latest` tag and a pinned release. This is the
  original behaviour and the rest of the run is unchanged.
- **`build`** — the script then asks which branch to build, `main` or `dev`,
  and builds the image from that branch before the stack files are
  generated. The image tag question is skipped, because the tag is derived
  from the build.

The build resolves the branch from `origin`: the selected branch is fetched
first, and the local branch is used only when no remote or fetch is
available. The resolved commit is checked out into a temporary detached
worktree, so your own checkout and any uncommitted work are left untouched;
the worktree is removed again once the build finishes, whether it succeeded
or failed.

The built image is tagged
`ghcr.io/turnstonelabs/turnstone:src-<branch>-<short-sha>`, and that tag is
written to `.env` as `TURNSTONE_IMAGE_TAG` — so the stack is pinned to
exactly the commit that was built. Because the tag exists only on this host,
`compose.override.yaml` also sets `pull_policy: never` on the `console`,
`server`, and `channel` services, and on every extra server node, so Docker
Compose never tries to pull it from a registry.

To move a source-built deployment onto newer commits of the same branch,
re-run the script with the same answers and then `docker compose up -d`: the
rebuild produces a new tag and rolls the services onto it.

### Server nodes

Node 1 is the `server` service in `compose.yaml`. A count above 1 generates
`server-2` … `server-N` into `compose.override.yaml`; each extends the base
`server` service and overrides only its identity (`TURNSTONE_NODE_ID`,
`TURNSTONE_ADVERTISE_URL`) plus, when mTLS is enabled, its certificate SANs.
Every node registers itself in Postgres on boot and the console discovers it
automatically — there is no static node list to maintain.

To change the count later, re-run the script with a new answer, then
`docker compose up -d --remove-orphans` to add or retire the containers.

### Workspace directory

Every `turnstone-server` node mounts one host directory at `/workspace` — the
place agents read and write project files. The script asks where that
directory should live and defaults to `workspace/` inside this folder.

**The directory must be named `workspace`.** The container mount point, the
Compose volume, and Turnstone's own terminology all use that single name, so
the script only ever creates and uses a directory called `workspace`. The
answer is therefore interpreted as follows:

| Answer | Result |
|--------|--------|
| A path ending in `workspace` that already exists | Used as-is. |
| A path ending in `workspace` that does not exist | Created, and the location is printed. |
| Any other path (e.g. `/home/you/Projects`) | Treated as the parent: `workspace` is created inside it (`/home/you/Projects/workspace`) and the location is printed. |
| A path that cannot be created (unwritable parent) | The script stops and prints the `sudo mkdir -p` and `sudo chown` commands to run before re-running it. |
| A path that exists but is not a directory | The script stops; choose another location. |

Relative answers resolve against this folder, and a leading `~` is expanded.
The resolved path is written to `.env` as `WORKSPACE_MOUNT`, which
`compose.yaml` bind-mounts into the `server` service and every extra node, so
all nodes share one workspace. It is also recorded in `setup-production.env`
as `TURNSTONE_SETUP_WORKSPACE_DIR` and offered as the default on the next run.

When the chosen directory sits inside the repository clone, the script adds it
to the repository-root `.gitignore` so nothing written there appears as
untracked repository content.

The directory is owned by the user running the script; the container runs as
UID 1000, so a workspace created by a UID 1000 host user is writable from the
nodes without further changes. To move an existing deployment to a different
workspace, re-run the script with the new location and then
`docker compose up -d`.

### Information needed per section

**OIDC single sign-on**

- Provider type: `authentik` or `generic`.
- Authentik: base URL, application slug, client ID, client secret, the
  Authentik group mapped to the Turnstone admin role, and the group mapped
  to general user access. The issuer is derived as
  `https://<authentik-host>/application/o/<slug>/` and the role claim is
  `groups` (Authentik's group membership claim).
- Generic: issuer URL, client ID, client secret, login button label,
  scopes, role claim, the claim value mapped to the admin role, the claim
  value mapped to general users, and optional extra trusted endpoint
  hostnames.
- Both: the public origin browsers use to reach Turnstone (the redirect
  base), whether the provider resolves to a private/internal address, and
  whether to disable password logins (SSO-only mode).

Role bindings map onto the built-in roles: the admin value →
`builtin-admin`, the general-users value → `builtin-operator`. See
`docs/oidc.md` for the full reference.

**TLS / front end**

- TLS: no further input; the mTLS overlay is added to the compose chain.
- Reverse proxy: `caddy` or `traefik` — see
  [Dashboard front end](#dashboard-front-end).
- Public DNS (Caddy only): the hostname Turnstone should be reachable at, a
  Let's Encrypt registration email, the DNS challenge provider (Cloudflare,
  Route 53, or Duck DNS), and that provider's credentials:
  - Cloudflare: a DNS API token with `Zone:DNS:Edit` (`CF_DNS_API_TOKEN`)
  - Route 53: an AWS access key ID and secret access key
  - Duck DNS: the account API token
- The script writes a `Caddyfile` for the domain with a DNS-01 challenge
  and a `caddy/Dockerfile` that builds Caddy with the matching DNS plugin,
  publishing ports 80 and 443.

**LLM backend**

- OpenAI-compatible base URL, API key, and an optional default model alias.

**Channel gateway**

- Discord: bot token and guild ID. Slack: bot token and app-level token.

## Answers file

`setup-production.sh` maintains a persistent answers file at
`deploy/auto-deployment/setup-production.env`. The file is written with mode
600 and is gitignored (it may contain OIDC client secrets and channel tokens).

### What the file does

- **First run** — the file does not exist yet; the script creates it at the
  end of a successful run, recording every answer given.
- **Subsequent runs** — answers from the previous run are loaded as defaults
  before any prompt is shown. If you press Enter at a prompt without typing
  a new value, the prior answer is reused.
- **After each run** — the script writes the current answers back so the
  file stays up-to-date. It **never** modifies the `AUTORUN` flag.

### Secrets are not stored here

Secret answers are written to the file as **blank placeholders** with a
comment naming the file that actually holds the value:

| Secret | Lives in |
|--------|----------|
| `POSTGRES_PASSWORD`, `TURNSTONE_JWT_SECRET` | `.env` |
| `OPENAI_API_KEY`, `CF_DNS_API_TOKEN`, AWS and Duck DNS tokens | `.env` |
| Discord and Slack tokens | `.env` |
| `TURNSTONE_OIDC_CLIENT_SECRET` | `config/turnstone-oidc.env` |

On every later run the script reads those files, shows a masked preview such
as `1fbe…FtV (128 chars)`, and asks whether to keep the value. Answering yes
reuses it without retyping; answering no prompts for a replacement. Under
`AUTORUN=true` the keep-existing answer defaults to yes, so automated runs
never need secrets in the answers file.

Deployments generated before the rename are handled too: if `.env` has no
`OPENAI_API_KEY`, a legacy `LLAMA_API_KEY` is picked up instead.

### AUTORUN flag

The first non-comment line of the file is:

```
AUTORUN=false
```

| Value | Behaviour |
|-------|-----------|
| `false` (default) | Script prompts interactively; values in the file are pre-filled defaults. |
| `true` | Fully non-interactive. The script uses only values from the file (and any exported environment variables); it never stops for user input. If a required value for an enabled section is missing the script exits immediately with an error naming the missing variable. |

**Only you should change this flag.** `setup-production.sh` never modifies it.

### Input precedence

From highest to lowest:

1. **Exported shell environment variable** — set before running the script,
   e.g. `TURNSTONE_SETUP_OIDC=n ./setup-production.sh`
2. **Value in `setup-production.env`** — loaded at startup
3. **Interactive prompt / built-in default** — what you type at the prompt,
   or the bracketed default if you press Enter

### Non-interactive runs

**Via the answers file (recommended):**

1. Run the script once interactively to generate and populate
   `setup-production.env`.
2. Edit the file to set `AUTORUN=true`.
3. On future reruns the script completes with zero prompts.

**Via exported environment variables (original method, still works):**

```bash
TURNSTONE_SETUP_MODE=production \
TURNSTONE_SETUP_CUSTOM_NAME=n \
TURNSTONE_SETUP_IMAGE_SOURCE=prebuilt \
TURNSTONE_SETUP_IMAGE_CHANNEL=latest \
TURNSTONE_SETUP_NODE_COUNT=1 \
TURNSTONE_SETUP_WORKSPACE_DIR=/srv/turnstone/workspace \
TURNSTONE_SETUP_OIDC=n \
TURNSTONE_SETUP_TLS=n \
TURNSTONE_SETUP_PROXY=caddy \
TURNSTONE_SETUP_PUBLIC_DNS=n \
TURNSTONE_SETUP_LLM=n \
TURNSTONE_SETUP_CHANNELS=n \
./setup-production.sh
```

For a source build, replace the first two image variables with
`TURNSTONE_SETUP_IMAGE_SOURCE=build` and
`TURNSTONE_SETUP_BUILD_BRANCH=main` (or `dev`);
`TURNSTONE_SETUP_IMAGE_CHANNEL` is not consulted on that path.

For a Traefik front end, set `TURNSTONE_SETUP_PROXY=traefik` plus
`TURNSTONE_SETUP_TRAEFIK_INCLUDED=y` or `=n`, and the matching
`TURNSTONE_SETUP_PROXY_*` / `TURNSTONE_SETUP_TRAEFIK_*` variables;
`TURNSTONE_SETUP_PUBLIC_DNS` is not consulted on that path.

Exported variables override both the answers file and interactive prompts.

## Starting the stack

```bash
cd deploy/auto-deployment
docker compose up -d
```

Docker Compose merges `compose.yaml` and `compose.override.yaml`
automatically, so plain `docker compose` commands in this folder pick up the
generated deployment settings. When mTLS is enabled the script also writes
`COMPOSE_FILE` to `.env` to append `tls.compose.yaml` to that chain.

## Post-deploy

1. Open the dashboard:
   - Public DNS: `https://<your-hostname>`
   - Otherwise: `https://localhost:8443` and trust Caddy's local root once:
     `docker compose exec caddy cat /data/caddy/pki/authorities/local/root.crt`
2. Create the first admin account via the setup wizard (required even in
   SSO-only mode — the wizard is only available while no users exist).
3. Open the **Models** tab and connect at least one LLM backend, e.g. an
   OpenAI-compatible endpoint such as `http://host.docker.internal:8000/v1`.
4. If SSO is enabled, sign in with the identity provider and confirm the
   admin and general-user group bindings behave as expected.

## Maintenance

- Re-run `./setup-production.sh` whenever hostnames, credentials, or
  feature choices change; it regenerates the files in place.
- Moving the workspace to another host directory is a re-run away: give the
  new location, then `docker compose up -d`. Existing files are not copied
  across — move them yourself before restarting the stack.
- `.env` and `config/turnstone-oidc.env` contain secrets and are written
  with mode 600 — keep them private.
- `setup-production.env` is also mode 600 and gitignored; it may contain
  OIDC client secrets and channel tokens.
- To update a pinned deployment, re-run the script and pin the new tag,
  then `docker compose up -d` to roll the services.
- To update a source-built deployment, re-run the script with the same
  branch to rebuild at the branch's current commit, then
  `docker compose up -d`. Old `src-<branch>-<short-sha>` images stay on the
  host until removed with `docker image rm`.

## Recovering from a failed or interrupted deployment

Both the setup script and the compose stack are safe to re-run. Nothing
about a failed first attempt is permanent — pick the right rerun below.

### Which command to re-run

| Situation | Fix |
|-----------|-----|
| `docker compose up -d` failed or was interrupted (pull error, build error, unhealthy container, network drop, Ctrl-C) | Fix the underlying cause if any, then run `docker compose up -d` again from this folder. It is idempotent: finished steps (pulled images, created volumes/networks, healthy containers) are kept and only the missing pieces are retried. **Do not** re-run the setup script for this. |
| You answered a setup prompt incorrectly (wrong hostname, token, group name, …) | Re-run `./setup-production.sh` with the corrected answers, then `docker compose up -d` to apply. The script regenerates the files in place; existing data volumes are untouched. |
| You want a completely clean retry | `docker compose down` (add `-v` **only** if you also want to delete the database and all data), re-run `./setup-production.sh` if the configuration needs to change, then `docker compose up -d`. |

### Common first-run interruptions and what they mean

- **`pull access denied for turnstone-caddy, repository does not exist`** —
  older generated overrides let Compose try to *pull* the locally-built
  Caddy DNS image before building it. The message was harmless (Compose
  fell back to building the image) but alarming. Overrides generated by the
  current script set `pull_policy: build` so the pull is never attempted;
  re-run `./setup-production.sh` to regenerate `compose.override.yaml` if
  you still see it.
- **`WARN Docker Compose requires buildx plugin to be installed`** — the
  Caddy DNS image was built with Docker's deprecated legacy builder because
  the buildx plugin is missing. The build still works today; install
  `docker-buildx-plugin` to remove the warning and future-proof builds.
- **Network failures while pulling images** (timeouts, DNS errors,
  `connection reset`) — nothing to clean up. Restore connectivity and run
  `docker compose up -d` again; already-downloaded layers are cached and
  the pull resumes.
- **`dependency failed to start: container turnstone-console-1 is
  unhealthy`** (or another service reported unhealthy) — a service did not
  pass its health check within the allowed window, so dependents were not
  started. On a first boot this is often transient (database
  initialisation, mTLS certificate bootstrap, and image extraction all
  land at once). Check the reason first:

  ```bash
  docker compose ps
  docker compose logs console        # or the failing service name
  ```

  If the logs show only slow startup, `docker compose up -d` again — the
  already-healthy services are left alone and only the failed ones are
  restarted. If the logs show a configuration error (for example an
  unreachable OIDC issuer, or an issuer that resolves to a private address
  without the private-network opt-in), re-run `./setup-production.sh` with
  corrected answers and then `docker compose up -d`.
- **Let's Encrypt / DNS-challenge errors in the caddy logs** — verify the
  DNS record points at this host and the DNS provider token is valid, then
  `docker compose up -d` (or `docker compose restart caddy`). Caddy retries
  certificate issuance on its own; no state needs deleting.

### Rerun behaviour of `setup-production.sh`

- The script only writes files; it never starts containers, so stopping it
  midway leaves the running stack (if any) untouched. If it stops before
  the final "Setup complete" message, simply run it again — partially
  generated files are overwritten.
- On rerun, prior prompt answers are loaded from `setup-production.env` and
  used as defaults (or used without prompting when `AUTORUN=true`).
- **`TURNSTONE_JWT_SECRET` and `POSTGRES_PASSWORD` are automatically
  preserved from the existing `.env` on every rerun.** The script reads the
  current values from `.env` before overwriting it, so the Postgres data
  volume and the new `.env` always stay in sync. Fresh random values are
  only generated on a first run when no prior `.env` exists.

## Troubleshooting

### `FATAL: password authentication failed for user "turnstone"`

**Cause:** The `POSTGRES_PASSWORD` in `.env` does not match the password
stored in the Postgres data volume (`turnstone_postgres-data`, or
`${COMPOSE_PROJECT_NAME}_postgres-data` if `COMPOSE_PROJECT_NAME` is set).
This happens when an existing volume is paired with a newly-generated
password — the Postgres image only applies `POSTGRES_PASSWORD` on first
initialisation of an empty data directory and never updates an existing one.

**Common scenario — fresh clone on a host that previously ran Turnstone:**
After `git clone` and `./setup-production.sh`, no `.env` exists yet, so
the script would normally generate a fresh random password. If the Docker
named volume `turnstone_postgres-data` still exists from a prior deployment,
that new password would not match the one stored in the volume.

**How `setup-production.sh` now handles this:**

Before generating a new `POSTGRES_PASSWORD` the script checks whether the
volume `turnstone_postgres-data` (or `${COMPOSE_PROJECT_NAME}_postgres-data`
if that variable is set) already exists:

- **Interactive run (TTY present):** you are warned and offered three choices:
  - **enter** — type the existing password; it is stored in `.env` and the
    volume is reused with all its data intact.
  - **wipe** — the volume is removed (all data deleted) after explicit
    confirmation, and a fresh password is generated.
  - **abort** — the script exits with instructions.

- **Non-interactive run (`AUTORUN=true` or no TTY) without a supplied
  password:** the script exits immediately with an error that names the volume
  and lists the three remediation options. Supply the password in one of these
  ways then rerun:
  1. Export it before running: `export POSTGRES_PASSWORD=<existing-password>`
  2. Add it to `setup-production.env`:
     ```
     POSTGRES_PASSWORD=<existing-password>
     ```
  3. Or remove the stale volume first (destroys all data):
     ```bash
     docker volume rm turnstone_postgres-data
     ```

**If you are already in a broken state** (passwords diverged before this
version of the script), choose one of these remedies:

1. **Restore the old password** — if you have the old `POSTGRES_PASSWORD`
   value, put it back in `deploy/auto-deployment/.env` then run
   `docker compose up -d`.

2. **Update the database password** — connect to the running Postgres
   container and change it to match the value now in `.env`:

   ```bash
   docker compose up -d postgres
   docker compose exec postgres psql -U turnstone \
       -c "ALTER USER turnstone WITH PASSWORD '<value from .env>';"
   docker compose up -d
   ```

3. **Full wipe** — if you have no data worth keeping, destroy the volume
   and let Postgres reinitialise with the current password:

   ```bash
   docker compose down -v
   docker compose up -d
   ```
